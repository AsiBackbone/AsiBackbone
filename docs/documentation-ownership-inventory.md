# Documentation Ownership Inventory

> Planning artifact for [issue #671](https://github.com/AsiBackbone/AsiBackbone/issues/671).
>
> **Scope:** classification and migration planning only. This inventory does not move, delete, redirect, or rewrite any article.

## Audit basis

This inventory was produced from the `issue_work` branch after the implementation-first DocFX navigation refactor. The DocFX build publishes `articles/**/*.md`, so every Markdown file currently under `docs/articles/` is in scope.

- Published articles inventoried: **155**
- **KEEP:** 118
- **REFACTOR:** 7
- **REDIRECT:** 1
- **MOVE/COPY-THEN-REDIRECT:** 6
- **ARCHIVE:** 23
- **REMOVE:** 0

No article is recommended for immediate removal. The repository has enough historical, release, design, and inbound-link value that deletion should only occur after a later migration verifies replacement URLs and inbound links.

## Classification rules

| Disposition | Meaning for this audit |
| --- | --- |
| **KEEP** | Authoritative AsiBackbone product, package, API, runtime, integration, security, release, sample, or maintainer documentation. |
| **REFACTOR** | Keep the current AsiBackbone URL, but narrow the page to concrete product behavior and send broader education to Learning. |
| **REDIRECT** | The current page should become a short product-specific pointer to the canonical Learning treatment. |
| **MOVE/COPY-THEN-REDIRECT** | Copy unique educational material to Learning before replacing the existing AsiBackbone page with a stable pointer. |
| **ARCHIVE** | Preserve the material in AsiBackbone as historical/design/release evidence, but move it out of the current-docs path after inbound links are mapped. |
| **REMOVE** | Delete only after proving the content is obsolete and a safe URL/link plan exists. No current article meets that threshold. |

## Ownership rules applied

1. **AsiBackbone remains authoritative for concrete software truth.** Package behavior, public APIs, host boundaries, security posture, operations, compatibility, release records, samples, and maintainer evidence stay here.
2. **Learning owns general education.** Architecture teaching, conceptual lineage, stack-neutral patterns, cross-tool comparisons, and broader framework explanation should be canonical in [AsiBackbone/Learning](https://asibackbone.github.io/Learning/).
3. **Stable URLs come before cleanup.** A MOVE, REDIRECT, or ARCHIVE disposition is not permission to delete the current file. Inbound links must be mapped first and the current URL should remain as a stub when needed.
4. **Historical evidence is preserved.** Old readiness reviews, alpha boundary records, and superseded design notes should move to an archive rather than disappear.
5. **Product-specific crosswalks remain product-owned.** Regulatory or standards pages that map directly to implemented AsiBackbone primitives remain here, even when Learning separately teaches the underlying external frameworks.

## Duplicate-authority findings

The main duplication risk is not implementation documentation; it is pages that teach the broader governance architecture while also appearing beside package/API truth.

- `asi-backbone-concept.md`, `equations-and-toy-models.md`, `intent-to-execution-pattern.md`, and `gateway-and-regional-policy-flow.md` contain organization-level conceptual teaching that should become canonical in Learning.
- `enterprise-adoption-personas.md` and `governance-tool-comparisons.md` are educational/comparative material better maintained in Learning.
- `why-asi-backbone.md` overlaps the educational rationale that Learning should own; the product repository only needs a concise fit/boundary pointer.
- `terminology-map.md` and `glossary.md` are useful in this repository only where they map concrete package vocabulary to actual APIs. Broader terminology should not form a second canonical glossary.
- `dynamic-liability-handshake.md` should remain product-owned for implemented acknowledgment types and lifecycle semantics, while Learning owns the broader conceptual and ethical history.
- `use-cases.md` and `government-and-regulated-systems.md` should remain only as concrete product-fit/host-obligation guidance; generalized scenario education belongs in Learning.
